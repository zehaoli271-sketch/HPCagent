# 数据口径

依据为超算平台工作人员回复及 Slurm 官方资料。两封后续回复确认了运行阶段的 CPU 记账时机、`seff` 内存取数及实时监控来源。

- 作业 CPU 时间累计有效步骤的 `time.total`，排除 `extern`。`batch` 仅含脚本自身。管理员确认 `time.total` 在步骤结束后写入，运行中的步骤只有 `elapsed`。步骤已经结束但 CPU 记账报告为零的原因仍需结合该条记录核对。
- 有效运行时间用 `end - start - suspended` 计算。历史样本中部分记录的 `elapsed` 已扣除挂起。实现会校验 `elapsed` 是否等于起止差或有效运行时间。`start=4294967294` 表示从未开始。
- 步骤级 `tres.requested.max` 中 `type=mem` 是单任务 MaxRSS，单位字节，`node/task` 标识峰值任务；不能直接当作作业总峰值。
- 作业级 `tres.allocated`、`tres.requested`、`required.*` 及步骤级 `tres.allocated` 的内存单位为 MB。步骤级 `tres.requested.*`、`tres.consumed.*` 为字节。
- 历史作业的 `seff` 内存估算取各步骤 `tres.requested.total[type=mem].count` 的最大值。每个步骤的 `total` 是其中各任务内存峰值之和，任务峰值可能发生在不同时间，作业的并发总峰值需用同一时刻的作业级监控数据计算。与 `seff` 对照时使用分配量作分母，分配字段按每 MB 为 1,048,576 字节换算。申请冗余筛查使用同一估算除以申请量。必要步骤缺数时只保留已取得的估算证据。[Slurm 记账说明](https://slurm.schedmd.com/accounting.html) · [seff 源码](https://github.com/SchedMD/slurm/blob/master/contribs/seff/seff)
- 固定 CPU 分配且统计完整时，作业平均 CPU 效率可按累计 CPU 时间除以分配 CPU 数与有效运行时间的乘积计算。分配变化、步骤缺失、重启/重新排队需单独核实。

## 实时检测的数据路径

管理员确认平台向参赛团队提供 Slurm 透传接口，历史查询慢属于上游 Slurm 的行为。平台允许团队在现有接口上二次封装，赛题侧重在作业仍在运行时识别低效。

- 实时路径通过 Slurm 获取当前运行作业及资源分配，通过 Prometheus 获取有权限的作业级 cgroup 用量。CPU 窗口效率使用累计 CPU 用量的差值，分母对应同一段内的分配容量。内存并发峰值应按同一采样时刻合计作业各节点的用量，再在窗口内取最大值。
- 依照提供的接口说明，已接入 `cgroup_info`、`cgroup_cpu_total_seconds` 和 `cgroup_memory_used_bytes`。仅汇总已匹配的作业根 cgroup，并要求全部分配节点有有效覆盖。节点对齐、幂等更新和限流已用合成样本验证，站点采样间隔及权限仍待真实连接核对。[交大 HPC Prometheus 接口说明](https://365.kdocs.cn/l/cbnicDizZDI2)
- 后台每轮发布短期内存快照，展示页与对话工具读取同一结果。历史复盘用完成后的 Slurm 记账和现有续查机制。查询范围、采样覆盖、数据来源和更新时间随结果展示。
