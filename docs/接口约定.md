# 前端与智能体接口约定 v1（团队待确认）

本文件记录诊断 HTTP 接口及当前 Python 工具接口。`frontend/mock/` 提供示例。修改字段、单位或语义时同步文档、示例和消费者。

## 工作边界

- 前端负责输入、查询状态、作业与步骤展示、证据和错误提示；不计算诊断指标，不直接访问超算 API，不持有凭据。
- 智能体服务负责理解请求、查询授权数据、调用确定性计算工具、输出结构化证据；不调用修改、取消或提交作业的接口。
- `core/` 负责字段转换、质量检查和指标计算；大模型不得自行创造数值。
- 首版采用 HTTP JSON、UTF-8、一次请求返回完整结果；暂不要求流式响应、登录或持久化会话。实际服务不应在未经授权的公共网络部署。

### 连接 SJTU HPC

网页向同源的 `POST /api/v1/hpc-connection` 提交 `{"token":"<访问令牌>"}`。服务器用运行作业接口验证读权限，成功后用只含随机标识的 HttpOnly 会话 Cookie 关联后端令牌。热图与诊断读取同一会话的数据源。`GET` 查询连接状态，`DELETE` 断开浏览器连接。令牌保存在本地服务进程内，浏览器不保存令牌值。启动后尚未配置账号或令牌时，首页等待连接。检测到 401 或 403 时显示令牌或权限问题。演示服务仅提供合成数据，连接请求返回 409 并提示使用正式服务网址。

## 入口：POST /api/v1/diagnoses

请求体示例：

```json
{"question":"分析作业 10001 的 CPU 使用情况","job_id":"10001"}
```

`question` 为 1 至 300 字的非空字符串。`job_id` 为数字字符串，可省略或为 null。问题可指定一个作业 ID 或一个完整历史时刻，支持「2026年11月22日17:00」及 ISO 8601。未指定时区时按北京时间处理。范围冲突或含糊时返回 `needs_clarification`。历史时刻查询可传 `mode`（`auto`、`lifetime` 或 `window`）。默认 `auto`，按整段平均利用率筛查，问题明确要求时刻前 5 分钟时使用监控。直接指定 `lifetime` 或 `window` 可以选定口径。

响应采用统一对象：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `schema_version` | string | 固定 `1.0` |
| `request_id` | string | 服务为请求生成的排查标识，不包含凭据 |
| `status` | string | `complete`、`insufficient_data`、`needs_clarification`、`error` |
| `message` | string | 面向用户的状态说明 |
| `data_source` | object 或 null | 数据来源和时间；未知字段用 null |
| `job` | object 或 null | 作业与步骤；未查到时为 null |
| `diagnosis` | object 或 null | 事实、原因假设、缺口和建议；未形成报告时为 null |
| `error` | object 或 null | 出错时的代码与安全提示 |
| `screening` | object 或 null | 历史时刻的筛查口径、覆盖计数、数据缺口和候选列表 |

完整响应见 `frontend/mock/complete.json`、`insufficient_data.json`、`error.json`。字段固定出现；可空值使用 JSON `null`，空列表使用 `[]`，不能将缺失值写成 0。前端忽略未来新增字段，未知状态展示通用提示而不是假设成功。

### 来源及时间

`data_source` 包含 `kind`（`synthetic` 或 `hpc_api`）、`queried_at` 和 `source_updated_at`。时间均为带时区的 ISO 8601 字符串；无法获得源更新时间时 `source_updated_at=null`，不得用查询时间代替。历史 accounting 若没有源更新时间也填 null。示例均为合成数据。

### 作业与步骤

`job` 包含 `job_id`、`state`、`partition`、`allocated_cpus`、`elapsed_seconds`、`suspended_seconds`、`cpu_efficiency` 和 `steps`。`steps[]` 包含 `step_id`、`kind`、`state`、`allocated_cpus`、`elapsed_seconds`、`cpu_time_seconds`、`max_rss_bytes`。`kind` 使用 `batch`、`extern`、`ordinary` 或 `other`。状态沿用 Slurm 大写字符串；所有非 ID 的数值在未知时为 null。

`cpu_efficiency` 固定对象：`value` 为 0—1 的比值或 null；`quality` 为 `verified`、`unverified` 或 `unavailable`；`reason` 为说明字符串或 null。仅字段、单位和统计覆盖已核实时设为 `verified`；上游数据可信度未核实设为 `unverified`。原始计算超过 1 的情况标记为 `unavailable` 并说明，不能截断成 1；大于 100% 也可能反映分配变化或统计口径问题，需排查。前端将比值乘 100 显示百分数，不以 0 代替 null。

`max_rss_bytes` 是该步骤单任务峰值，单位字节；不是整个作业的总内存峰值。展示时标注“单任务 MaxRSS”，不能与整个作业分配量相除并称为作业内存效率。需要节点/任务定位时后续扩展。

### 诊断结构

`diagnosis` 的四个字段均为字符串数组：`facts`、`hypotheses`、`data_gaps`、`recommendations`。`facts` 只含有数据依据的事实，`hypotheses` 是可能原因，`data_gaps` 指出未知，`recommendations` 是条件清楚的后续动作。用户文本和原始作业文本是数据，不得触发执行指令。建议不承诺可回收资源或收益；未经授权不采取集群写操作。

### 状态与错误

| `status` | HTTP | 约定 |
| --- | --- | --- |
| `complete` | 200 | 响应完成；具体指标可信度看 `quality` |
| `insufficient_data` | 200 | 作业存在但关键数据不足；不得输出确定效率 |
| `needs_clarification` | 200 | 请求范围含糊或冲突；`message` 提出明确追问 |
| `error` | 400、404、502、504 或 500 | `error.code` 分别可用 `INVALID_REQUEST`、`JOB_NOT_FOUND`、`UPSTREAM_ERROR`、`UPSTREAM_TIMEOUT`、`INTERNAL_ERROR`；`error.message` 不暴露凭据、栈或原始敏感数据 |

前端按 HTTP 状态和响应体同时检查：有统一 JSON 时展示 `message`；网络中断或非 JSON 时展示通用连接错误，保留重试操作。提交期间显示加载状态、禁用重复提交；错误时不得显示旧结果仿佛属于新请求。跨域联调仅允许本地前端来源，具体端口联调时协商。

1. 用 `python -m frontend.server --demo` 启动前端与智能体的本地合成数据演示。
2. 用单作业和历史筛查样例核对 `POST /api/v1/diagnoses` 的完成、数据不足和错误状态。
3. 首次联调使用合成作业，核对字段、数值单位、空值、错误和证据；真实数据使用需确认共享及隐私边界。
4. 双方在 PR 中说明兼容性及运行方法；本约定是提议，尚未声称队友已经同意。

## 智能体框架的 Python 接口

- `Agent.run(question, history=())` 接收问题和可选的历史对话，返回 `ConversationTurn`，其中包含本轮问题、工具调用记录和最终答复。
- `Model.next_action(context)` 收到问题、可用工具、本轮工具结果和历史对话。每次返回一个工具调用或一条最终答复。单个问题默认最多执行四次工具调用。
- `Tool` 由工具名称、说明、参数 JSON Schema 和执行函数组成。工具接入时，执行函数负责校验参数，并返回 `ToolSuccess` 或 `ToolFailure`。已知失败用错误代码和面向用户的消息表示。
- `ToolSuccess` 携带最少必要的脱敏数据及证据。证据包含来源、查询范围、获取时间和可选的数据源更新时间。时间用带时区的 ISO 8601 字符串。未来的数据工具需在结果内表达数据完整程度和指标是否可信。
- 答复状态包含完成（`answered`）、待澄清（`needs_clarification`）、证据不足（`needs_data`）和达到工具调用上限（`tool_limit`）。
- 授权后的平台查询和令牌管理在应用后端实现，模型上下文只接收查询所需的字段。

## Slurm 作业查询

`query_slurm_jobs` 接收带时区、精确到秒的 `start` 和 `end`，以及 `time_basis="usage"`。后端将时间转换成 Unix 秒，通过 `start_time` 和 `end_time` 调用 `GET /slurmdb/jobs`。设置 `SJTU_HPC_API_TOKEN` 后注册该工具。

`core.slurm_jobs.fetch_slurm_jobs` 为后端提供响应中的作业记录，供后续 CPU、内存和筛查逻辑复用。模型收到本次响应的条数、覆盖标记、警告数量和最多 20 条预览。预览字段限作业 ID、状态、提交时间、可调度时间、开始时间和结束时间。接口覆盖度未验证，结果数量表示当前令牌下本次响应中的记录数。

### 时间窗口核查

在历史归档中选取首、中、末三个 60 秒窗口，按北京时间检查返回记录。每行统计的是响应中的记录数。

| 窗口开始 | 返回条数 | 窗口结束时尚未开始且已可调度 | 开始和结束时间分别落在窗口两侧 |
| --- | ---: | ---: | ---: |
| 2026-11-01 00:00 | 3,855 | 1,099 | 2,559 |
| 2026-11-08 12:00 | 3,563 | 724 | 2,612 |
| 2026-11-16 00:00 | 5,175 | 1,612 | 3,232 |

这些响应支持按记账时间范围查询的解释。Slurm 25.11.2 在没有指定状态或作业 ID 且提供两个边界时，依据可调度时间和结束时间匹配。这个上游条件与三窗现象一致。部分历史记录保留了完整的跨窗时间戳，归档响应未记录当时是否显式发送了开关。 [Slurm 25.11.2 筛选源码](https://github.com/SchedMD/slurm/blob/slurm-25-11-2-1/src/plugins/accounting_storage/mysql/as_mysql_jobacct_process.c#L1589-L1636)

上游解析器列出 `usage_time_as_submit_time` 和 `disable_truncate_usage_time`。交大网关规格文件需要认证，已提供的接口目录 PDF 未展开参数。当前网关对两个开关的处理仍待有权限的对照查询验证。 [Slurm 25.11.2 参数源码](https://github.com/SchedMD/slurm/blob/slurm-25-11-2-1/src/plugins/data_parser/v0.0.44/parsers.c#L9127-L9137)

有授权令牌时，可以在同一个短窗口内逐一切换参数。验证提交口径时，选取提交、可调度和开始时间分开的已知作业，比对返回的作业集合。验证截断行为时，选取起止分别位于窗口两侧的已知作业，对照默认结果、`disable_truncate_usage_time=true` 和 `false` 的作业及步骤时间戳。HTTP 200 只表明请求成功，参数是否生效需要通过对照结果确认。

在仓库根目录运行以下命令。时间仅作格式示例，可以换成授权账号能看到已结束作业的历史窗口。可加 `--job-id ID` 将本地对比限定到一个已知作业。

```powershell
python -m experiments.probe_slurm_job_time --start "2026-11-08T12:00:00+08:00" --end "2026-11-08T12:01:00+08:00"
```

命令从 `SJTU_HPC_API_TOKEN` 读取令牌，先查基线，再分别请求提交标志为 `true`、禁止截断为 `true` 和 `false`。结果只汇总作业集合、时间变化、窗口边界和警告数量。各次响应都相同时，实验结论为未能验证，需要换成能区分两种行为的样本。

## 单作业 CPU 分析

`analyze_job_cpu` 通过 `GET /slurmdb/job/{job_id}` 取作业详情。它接收数字 `job_id`，可传 `cluster` 和 `start_time`（Unix 秒）区分同 ID 的记录。匹配到唯一记录时才进入分析。工具调用和数值计算已用模拟响应验证，交大详情端点仍待授权联调。

`core.job_cpu.analyze_job_cpu` 接收完整的作业记账记录，可独立调用。它沿用离线原型的作业级口径，累计非 `extern` 步骤的 `TotalCPU`，用实际分配 CPU 数乘以 `end - start - suspended` 得到容量。`elapsed` 用于校验时间，兼容上报值已扣除挂起的情况。

已完成作业热图（`GET /api/v1/job-heatmap`）和试算接口（`POST /api/v1/cpu-efficiency`）都通过 `core.efficiency.calculate_job_efficiency` 调用同一个算法。适配层继续输出 `efficiency`、`cpu_seconds` 和 `reason`。数据不足时，利用率和用于展示的 CPU 秒数均为 `null`，`reason` 提供中文说明。

热图作业记录的 `cpus` 和 `requested_cpus` 分别为实际分配和申请的 CPU 核数。`memory_ratio` 使用分配内存作分母，单位为比例，内存用量与分配量以字节返回。运行作业使用对齐后的监控采样，已完成作业使用 `memory_basis` 指定的 seff 估算或已核实的作业级峰值。内存用量或分配量缺失时，内存效率留空。

CPU 和内存切换、筛选和排序在浏览器中作用于当前快照。自动刷新默认开启。关闭后，页面保留当前快照，支持手动读取最新快照。后台采集独立运行。

智能体工具的 `cpu` 对象包含 `availability`、`reason`、`formula_version` 和 `utilization`。可计算时，`utilization` 为 0 到 1 的比值，并附累计 CPU 微秒、分配 CPU 秒、有效运行秒数和纳入的步骤 ID。运行中、重启或调整分配、异构组件、步骤缺失、记账冲突和有平台警告的响应需要进一步核对，利用率留空。低效候选标签由后续筛查逻辑给出。

## 历史时刻 CPU 筛查

网页对话使用下文的 `POST /api/v1/chat`。`POST /api/v1/diagnoses` 是独立诊断入口，两者复用同一套单时刻筛查流程。

1. `find_jobs_running_at` 用作业记账中的 `start <= at < end` 判断。只有起点且仍报告运行中的记录可按持续运行处理。挂起、调整分配、重启、缺少区间或同号歧义计入 `uncertain_count`。真实应用使用短 usage 查询收集候选，接口覆盖尚未验证。
2. 默认用整段作业 CPU 口径计算当时在运行的作业的整段平均值，真实 usage 响应的截断边界仍待验证。用户要求时刻前五分钟时，`get_job_cpu_usage_window` 取作业级 CPU 秒计数器的实际样本差，容量为分配核数乘实际采样跨度。采样跨度至少覆盖请求窗口的 80%。返回实际观测起止，拒绝重置、无法归属、重复序列和超出容量的观测。
3. `screen_low_efficiency_jobs` 默认按低于 20% 的阈值生成复核候选，可用 `--cpu-threshold` 配置。提问要求「最低效的三个」或「CPU 利用率最低的 3 个」时，改用 CPU 利用率升序排名，最多返回请求的数量。排名响应的 `top_n` 是请求数量，`threshold` 为 null。结果带 `running_count`、`uncertain_count`、`evaluated_count`、`unavailable_count`、`candidate_count` 和 `candidates`。可评估条数少于请求数量时返回 `insufficient_data`，并列出已有证据的作业。

默认窗口工具使用交大作业级 cgroup 数据，按 Slurm 给出的分配节点读取并合并 CPU 样本。已有单序列部署可同时设置下面三项作为历史窗口查询的显式配置。节点级指标和 Prometheus 的 `job` 标签无法作为 Slurm 作业 ID。[交大 HPC Prometheus 接口说明](https://365.kdocs.cn/l/cbnicDizZDI2)

| 环境变量 | 内容 |
| --- | --- |
| `SJTU_HPC_JOB_CPU_METRIC` | 已确认的整作业累计 CPU 秒计数器，覆盖作业全部节点 |
| `SJTU_HPC_JOB_CPU_HOSTNAME` | 该指标对应的已授权、明确的 exporter 主机名 |
| `SJTU_HPC_JOB_CPU_ID_LABEL` | 唯一对应 Slurm 数字作业 ID 的标签 |

显式配置的单序列模式要求每个作业有唯一的整作业序列。默认 cgroup 模式要求每个分配节点有唯一的作业根 cgroup 序列。历史不可用时页面显示数据缺口。交大实际历史保留、返回权限和站点采样频率仍待授权联调。 [Prometheus 查询格式](https://prometheus.io/docs/prometheus/latest/querying/api/#instant-queries)

## 实时采集与快照

正式服务默认开启运行作业的全量采集。已授权的看板重新打开或刷新时恢复采集。`GET /api/v1/hpc-connection` 返回 `collection_enabled`，`null` 表示当前数据源不提供开关。页面顶部使用同源的 `POST /api/v1/live-collection` 提交 `{"enabled":true}` 开启，提交 `{"enabled":false}` 中断。两种操作都返回连接状态。中断会结束当轮及其限流等待，已发出的 HTTP 请求按原有超时收尾，HPC 连接及最近一次已发布的快照会保留。恢复时先取得新的作业目录，再开始新一轮采集。

开启后，后台独立刷新目录和采集监控数据。目录通过 `GET /slurm/jobs` 获取运行作业、分配节点和资源量。目录短时超时时，监控继续使用最近一次成功获取的目录，并标明目录更新时间和错误。目录超过三轮的间隔或 120 秒中的较大值后，快照标为过期，停止用于当前低效筛查。

浏览器连接成功后复用认证时取得的 Slurm 作业清单。使用启动凭据时首读一次目录。首轮监控发布前，热图用该清单显示方格，CPU 和内存效率为空，返回 `catalog_only: true` 和清单查询时间。目录的后续后台刷新将在下一次完整轮次发布时体现到热图上。

监控通过 `GET /prometheus/query_range` 按批读取 `cgroup_cpu_total_seconds` 和 `cgroup_memory_used_bytes`。每个选择器明确填写一个 `hostname`。返回序列按 Slurm 节点和作业根路径 `/slurm/uid_<uid>/job_<jobid>` 核对。查询同时读取 Prometheus 原始采样时间，去除重复评估点。网关拒绝批量请求时，降级为逐节点读取原始范围序列，优先读取 CPU。

- 完全相同的作业分配去重。同号但分配不一致、节点不完整、计数器重置和不可信的时段不会作为低效证据。根 cgroup 匹配用于排除步骤 cgroup，避免重复统计。
- CPU 使用所有节点重叠的实测时间段求差，按分配核数乘实测历时计算效率。分配和实测区间至少覆盖一分钟。内存选用最近一组覆盖所有分配节点的有效实测用量，节点样本时差不超过 30 秒。参考时间是该组的最后一个采样时间，结果同时显示时差。内存比例按 Slurm 可确认的分配量计算。缺少数据时，`memory_reason` 区分样本覆盖不足、样本过期、无法对齐和分配量待核实。
- Slurm 作业目录默认每 30 秒刷新。单次监控批量最多 8 个节点，本服务共享 30 次/分钟的 Prometheus 请求预算。整轮采集在额度用完时等待，完成后发布再开始下一轮。HTTP 429 暂停后续监控请求，使用服务端提供的等待秒数，缺省等待 60 秒，同时放慢后续请求，保留本轮进度。过期和部分覆盖都会标注，查询单个作业会优先安排其节点。
- 每次发布时清理超过 20 分钟的旧快照。断开连接或更换令牌会停止旧采集器。默认启动不打开 SQLite。历史时间范围按需走原有 Slurm 分窗和续查流程。

正式服务按整轮发布。每轮以开始时的节点清单为范围，将节点分组并最多并发读取 3 组，共用请求预算。真实样本较稀疏时，最多读取约 10 分钟的原始样本，用实际重叠区间计算。完成后再次按最新 Slurm 分配核对作业身份，在内存中原子发布快照。节点缺数和请求错误保留在覆盖统计中，指标标注原始采样时间。

`GET /api/v1/job-heatmap?view=running` 与对话工具 `get_live_jobs` 读取同一快照。响应包含作业列表、采集时间、可评估数量、节点覆盖、快照数量及采集状态。`collection_paused` 表示后台全量采集已暂停，首轮发布前此时返回 `status: "paused"`。`collection_revision` 是已发布轮次，`collection_seconds` 是本轮采集耗时。`GET /api/v1/live-updates` 在开启采集时使用同一授权会话推送版本号，首页收到新版本后读取已发布的快照。作业的观测时间超过 5 分钟可在详情中查看，当前低效筛查仅使用更近的实测值。`catalog_error` 报告 Slurm 目录读取错误，`coverage.errors` 报告监控读取错误，`coverage.cpu_gaps` 统计 CPU 待评估的原因。

同源 `POST /api/v1/live-job` 接收 `job_id`（数字字符串）及可选 `started_at`（Unix 秒）。确认暂停后台采集后，先等已发出的请求收尾，再按 Slurm 分配节点和作业根 cgroup 读取 15 分钟内的 Prometheus 样本。单节点直接读取原始时间戳，多节点使用带原始时间戳的批量查询。CPU 效率按各节点最近共同覆盖的最多 5 分钟计算，要求至少一分钟、计数不回退、末端样本不超过 6 分钟。此处的时间范围根据实测约 5 分钟的采样间隔确定。分配开始和调整时间明确时按 Slurm 时间限定区间，否则从服务确认分配起计算。分配清单默认每 60 秒按需核实。响应包含实际采样时间、样本缺口、`max_sample_age_seconds` 和 `next_poll_seconds`。全量采集启用时返回 409，正在收尾时返回 `waiting`。曲线跟随实际采样时间，接口限流时按返回等待时间续采。

## 作业对话

`POST /api/v1/chat` 接收 `application/json`。请求包含用户的 `question`、页面生成的随机 `chat_id`，以及可选的单时刻筛查口径 `mode`（`auto`、`lifetime` 或 `window`）。默认 `auto`，与诊断入口使用相同的口径选择。对话可以沿用上轮时刻追问「再看前 5 分钟」。同一页面沿用同一个 ID，换数据源或刷新页面时创建新对话。只读网页服务按连接会话与对话 ID 隔离内存状态，服务重启或旧对话被回收时需从新查询开始。前一轮执行期间同一对话的重复请求返回 409。

可翻页的结果附带 `page_id`。同源 `POST /api/v1/chat-page` 接收 `chat_id`、`page_id`、`page`，读取当前连接中该轮排序已固定的记录，返回 `records`、`page`、`pages` 和 `offset`。服务为每段对话保留最近 8 轮可翻页结果。点击页码只更新原表格，实现时不调用数据源或智能体。

查询首次向 HPC 取数时检查同一连接的后台采集。若已在采集，聊天结果的 `status` 为 `collection_conflict`，详情和诊断接口返回带相同状态的 HTTP 409。页面收到后询问用户，确认时先中断采集，再重试原查询。读取内存快照、已取得的对话结果和本地归档可以直接进行。空闲时先进入 HPC 查询的请求完成后，后台才继续取数。

后端为每轮分配 HTTP 工作线程，使用 UTF-8 NDJSON 逐行推送。远程进度包括已经成功的窗口数，断开连接后后端可在下一次推送时停止继续读取窗口。

结果中的作业 ID 按钮使用 `POST /api/v1/job-detail` 读取详情。JSON 请求传入 `job_id`（数字字符串）、`chat_id` 和结果附带的 `job_ref`。历史时刻结果可额外带 `point_at`（Unix 秒），供演示服务复现相同样本。接口优先复用当前会话的匹配快照，并通过作业标识区分同号记录。返回 JSON 详情与证据，聊天历史和筛选条件保留。

| 事件 | 内容 |
| --- | --- |
| `progress` | 状态文案及可选的 `completed`、`total` 和 `timed_out` 窗口数 |
| `result` | `data` 含确定性结果。可能包括查询口径、来源、覆盖、样本数、分页、质量检查与详情 |
| `delta` | 致远一号可选解读的一小段正文 |
| `notice` | 提示模型失败或查询条件经模型改写 |
| `done` | 本轮结束 |

### 时间解析和工具

时间在服务端以 Asia/Shanghai 解析。无年份的日期使用服务当年，区间采用 `[start,end)`，日期范围写到某日且未给时刻时包含该日。查询今天以当前时刻为截止点。普通日期范围默认按运行区间相交，明确的提交、开始、结束问题使用指定事件，首次逐日趋势默认按提交时间。提出「过去 N 天每天」时统计截至昨天的 N 个完整自然日。滚动时段比较使用相邻时间段，例如「最近 7 天并与前 7 天对比」。

「17:00 时已完成」按结束时间筛选，当天零点为默认起点，截止时刻计入，报告展示完整范围。「17:00 完成」按结束事件匹配该秒。「17:00 正在运行」使用单时刻运行筛查。CPU 整段利用率仍依据可靠的完成记账。

Agent 复用 `agent.runtime.Agent` 的工具注册与执行。明确的查询由 `agent/chat_intent.py` 解析。陌生表述可以由致远一号用原生工具调用提交规范化查询，再经过同一解析器和参数校验。复杂筛查根据候选是否存在决定继续获取详情。模型解读只接收摘要和有限的工具事实，资源数值来自 Python。

| 工具 | 功能 |
| --- | --- |
| `query_jobs` | 选择数据源，匹配时间范围、状态、分区和资源条件 |
| `get_job_detail` | 获取指定作业或上一轮排序条目的作业与步骤数据 |
| `get_data_coverage` | 查询采集窗、采样时长和归档作业事件的首末时间 |
| `aggregate_jobs` | 按状态或日期汇总，报告有效资源样本 |
| `detect_inefficient_jobs` | 按 CPU 或内存阈值筛查，按指标排序并估计候选差额 |
| `compare_jobs` | 对照主时间段与比较段，或查看所选作业同分区的样本 |
| `analyze_data_quality` | 报告缺失字段、零记账、尚未定稿状态、未开始标记及不可计算原因 |

### 数据源和指标限制

- SQLite 使用只读连接和绑定参数。采集窗记录采集范围，作业起止时间可能早于最早采集窗。报告中的文件更新时间是归档文件时间。查询的数据是归档保留快照，原始观测文件按原方式保存。
- 有授权连接时，单时刻和范围共用历史作业读取流程。请求协商 gzip，兼容未压缩 JSON。客户端按块读取响应，单个解压后的响应上限为 96 MiB。每个窗口的等待预算至多 25 秒，单轮为历史记账读取预留 120 秒。
- 范围查询从最多一小时一段开始。遇到超时、网关暂时不可用、响应过大或传输中断，从失败位置改为最多 15 分钟一段。短窗口失败后记录其范围，连续三个短窗口失败会暂停本轮。单时刻遇到暂时性故障可重试一次。401、403、429 等其他错误立即停止。
- 成功窗口保留在当前对话的内存快照中。点击「继续查询剩余窗口」只处理失败和未读的窗口。零个窗口成功时显示原因和进度，结果不包含作业计数。`windows_reused`、`covered_seconds`、`failed_windows` 和 `next_start` 记录续查与时间覆盖。服务重启或对话快照被回收后需重新读取。
- 流程只保留计算、识别作业和展示详情所用的记账字段。按作业标识、集群、提交时间及数组或异构组件归并，相关字段的变化版本及对应窗口保留在快照中。由于网关 usage 取数口径和截断尚待实测确认，报告只对实际返回的作业计算。贴近窗口边界的记录留出 CPU 整段指标。
- CPU 复用整段算法。观测为零、步骤缺失、仍在运行或从未开始的记录各自报告。异常状态单独复核。候选未用 CPU 秒是可评估样本的容量差，可供后续人工核查。
- 完成作业的默认内存筛查采用 seff 估算，即步骤级 `requested.total[mem]` 的最大值。筛查分母为作业申请量，详情还显示按分配量计算的 seff 内存效率。任一必要步骤缺少有效值时，详情只显示已有数据的估算值，筛查比例留空。
- 已确认有作业级并发峰值时，可通过 `--job-memory-peak-field` 与 `--job-memory-unit-bytes` 启用并发峰值口径。筛查内的分子来源应保持一致，详情可分别展示并发峰值、seff 估算及单任务 MaxRSS。指标口径见[数据口径](数据口径.md)。
- 同一对话的过滤、排序和序号沿用已获取的快照。带有「最新」「刷新」的查询重新取数。未给时间且当前没有时间条件时，最新范围查询默认最近一小时。分页默认每页 20 条。
